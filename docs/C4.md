# C4 — 공고 식별 규칙 (설계안)

담당 C · 2026-10-16 · **설계안(팀 리뷰 대기)** · 수집 배치 코드는 A1·C3·D5 의존으로 보류, 식별 규칙만 선행
근거: `spec.md` §4.1·§4.5·§15 / B1.md(applications 구조) / `Plan.md` 1-6절(서울시 실측)

## 풀어야 할 문제

서울시 공고엔 **고유번호·수정일이 없다.** 그런데 B1의 `applications`·`resumes`가 공고를 FK로 물고 있어서, **공고 내용이 바뀌거나 출처에서 사라져도 그 참조가 깨지면 안 된다.** 결국 "무엇을 공고의 **불변 신분증**으로 삼느냐"가 핵심이다.

## 식별 3층

- **내부 ID (불변)** — `job_postings.id` UUID. 모든 참조는 이것만 본다. 한 번 발급되면 안 바뀐다.
- **링크 키 (재식별용)** — 같은 공고를 다시 알아보는 자연키. 서울시는 고유번호가 없으니 `정규화(기업명 + 제목 + 접수방법)`을 해시. 내용이 바뀌어도 링크 키가 같으면 **같은 내부 ID 유지**. `(source, link_key)` 유니크. 사람인·공채속보는 출처 고유 ID를 그대로 링크 키로.
- **내용 해시 (변경 감지만)** — `정규화(기업명·제목·등록일·직종코드·지역코드·직무내용)` 해시. 링크 키 같고 해시 다르면 = **같은 공고의 내용 변경** → 내부 ID 유지 + 재임베딩. 마감일처럼 자주 바뀌는 값은 해시에서 빼고 필드만 갱신.

## 수집 때 로직 (하루 1회 전량 재수집)

```
링크 키로 기존 공고 조회
  없음           → 신규: 내부 ID 발급, insert, 임베딩
  있고 해시 같음  → 변화 없음: last_seen_at만 갱신
  있고 해시 다름  → 내용 변경: 내부 ID 유지, 필드·해시 갱신, 재임베딩

오늘 수집에 없는 공고
  → is_active=false (추천에서 제외), 행은 보관
  → applications·resumes가 참조 중이면 물리 삭제 금지
  → 참조 없고 N일 이상 안 보이면 삭제 후보
```

부분 수집 실패로 수천 건이 한꺼번에 사라진 것처럼 잡히는 사고를 막으려고, **수집 건수가 전일 대비 비정상 급감하면 삭제 단계를 건너뛰고 알림(D16)만** 보낸다.

## 아직 안 정한 것 (팀 합의 필요)

- 링크 키를 `기업명+제목+접수방법`으로 충분히 볼지 — 접수방법이 비거나, 같은 기업이 같은 제목으로 **재공고**할 때 같은 공고로 묶이는 문제
- 물리 삭제 유예 N일 (예: 참조 없고 30일)
- 완료성 가드 기준 (예: 전일 대비 80% 미만이면 수집 실패로 보고 삭제 중단)

## 누가 봐야 하나

- **B** — 공고 FK는 `job_postings.id`(불변 UUID)로 걸면 된다. "참조 중 공고는 물리 삭제 안 함" 정책만 합의되면 끝. `job_postings` 모델은 내가 만들어 넘긴다(마이그레이션은 B가 취합).
- **C15(내 파트)** — 지원 기록이 내부 ID 참조라 공고 내용이 바뀌어도 안전. 비활성 공고도 지원 현황 화면엔 보여야 함.
- **D** — 수집 CronJob(하루 1회)·완료성 알림(D16) 연계.
