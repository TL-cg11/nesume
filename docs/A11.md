## 1. 무엇을 돌려주는가

공고 요건을 뽑아 **세 갈래로** 나눈다.

| 상태 | 뜻 | 사용자가 할 일 |
|---|---|---|
| `covered` | 자소서 본문에 썼다 | 없음 |
| **`in_experience_only`** | **경험엔 있는데 자소서에 안 썼다** | **지금 바로 쓸 수 있다** |
| `missing` | 아무 데도 없다 | 해당 경험이 있는지부터 확인 |

가운데 칸이 이 기능의 값이다. 실제 출력이다.

```
키워드 11건  counts={'covered': 2, 'in_experience_only': 3, 'missing': 6}
필수 4건 → 세는 단위 3개, 달성률 33%

  in_experience_only  required   정보처리기사        ← 자격증
  in_experience_only  preferred  Docker            ← 교내 예약 서비스
  in_experience_only  mentioned  PostgreSQL        ← 교내 예약 서비스
  missing             required   소프트웨어학과 (택일)
  missing             required   엑셀
  covered             required   컴퓨터공학 (택일)
  covered             mentioned  Django
```

## 2. ★ 빠진 요건에는 문장을 만들지 않는다

매칭 분석의 가장 큰 위험은 **허위 기재 유도**다.

> "Python 이 빠졌습니다" 다음에 예시 문장을 붙이면 사용자는 **해 본 적 없는 일을 쓴다.**
> 자소서의 허위 기재는 면접에서 드러나고 **책임은 사용자가 진다.**

그래서 `missing` 에는 **질문만** 돌려준다.

```
- 「정보처리기사」 자격이 있습니까? 취득 예정이라면 그 사실을 쓰는 것도 방법입니다.
- 엑셀 활용 수준은 어느 정도입니까? 등급·자격이 있으면 함께 씁니다.
- AWS 사용 경험이 있습니까?
```

질문 목록 위에 안내를 **반드시 함께** 보여준다 — 없으면 사용자는 질문을 *채워야 할 빈칸*으로 읽는다.

> 해당 경험이 없으면 쓰지 않는 것이 맞습니다. 없는 경험은 면접에서 드러납니다.

모델이 문장을 만드는 것은 `in_experience_only` **뿐**이다. 그쪽은 지어낼 필요가 없다.
A7 의 "STAR 요소가 2개 이하면 모델을 부르지 않는다" 와 같은 판단이다.

## 3. ★ 모델이 없는 기술을 끼워 넣으면 버린다

```
요청: "Docker" 를 넣은 문장을 만들어라 (근거: 도커로 배포 환경을 구성했습니다)
응답: "PostgreSQL 과 Redis 로 데이터를 관리했습니다"
       ^^^^^^^^^^^^^^ Redis 는 사용자 글·경험 어디에도 없다
→ 버린다. dropped_hints += 1
```

`service.parse_hints` 가 세 가지를 검사한다.

1. 대상 낱말이 `in_experience_only` 목록에 있나
2. 문장에 그 낱말이 들어 있나
3. **문장에 사용자 글·경험에 없는 사전 항목이 나오나** ← 가장 중요

3번이 없으면 **쓴 적 없는 기술이 자소서에 들어간다.** 버린 개수를 `dropped_hints` 로
돌려주므로 **측정할 수 있다** — 제공자가 정해지면 이 숫자가 모델 품질 지표가 된다.

## 4. 공고 본문을 모델에 보내지 않는다

```
연락처 → A1 mask → C5 preprocess_external_text → 규칙 기반 키워드 추출
                                                  ↓
                                        모델에 가는 것은 **낱말 몇 개**
```

순서는 `docs/C5.md` 가 정했다(C5 는 PII 를 다루지 않으므로 A1 이 먼저).
**키워드를 모델에게 뽑게 하면 공고 전문이 매번 프롬프트에 들어간다** — 외부 untrusted
텍스트가 공고 하나 길이만큼 프롬프트에 열린다. 규칙으로 뽑으면 그 표면이 사라진다.

A10 에서 배운 방법으로 **고정**했다 — 판정만 보지 말고 모델이 받은 프롬프트를 직접 본다.

```python
async def test_posting_body_never_reaches_the_model():
    assert POSTING_ONLY not in prompts(provider)
```

근거가 아닌 경험도 보내지 않는다. 보내면 모델이 그쪽 사실을 섞는다.

C5 가 찾은 인젝션 신호는 버리지 않고 `posting_flags` 로 돌려준다 → 감사(B11)·대시보드(D15).

## 5. 키워드 추출 — 두 갈래

| 갈래 | 대상 | 방법 |
|---|---|---|
| 구조화 필드 | `certificates` `computer_skills` `major` `preferred` | **구분자로 쪼갠다** |
| 줄글 | `job_content` `title` `job_name` | **사전으로 찾는다** |

구조화 필드를 사전으로만 보면 **사전 밖 요건을 통째로 놓친다** — 서울시 `CERTIFICATE` 에는
"요양보호사", "지게차운전기능사" 가 수없이 들어온다. 반대로 줄글을 구분자로 쪼개면
"것", "수행" 같은 조각이 요건이 된다.

버리는 조각: 마스킹 기호(`***`) · C5 중화 마커(`⟦…⟧`) · 불용어("무관", "해당없음") ·
숫자+단위("1급" — 앞 요건의 수식어가 떨어져 나온 것) · 25자 초과(문장이다).

**무게는 필수 / 우대 / 언급** 셋이다. 섞으면 **우대 사항이 빠진 것이 필수처럼 보인다.**
`preferred` 필드와 조각 안의 "우대"·"가점" 을 보고 내린다.

## 6. ★ 숫자를 믿을 수 있게 만드는 두 가지

**① 택일 묶음** — `MAJOR` 의 "컴퓨터공학, 소프트웨어학과" 는 **둘 다 하라는 말이 아니다.**
따로 세면 전공을 맞춘 지원자도 달성률이 절반으로 나온다. `major` 에서만 나온 요건끼리
한 묶음으로 세고, 화면에 "택일" 로 표시한다.

**② 믿을 수 있는지 함께 돌려준다** — 키워드가 2개인 공고의 "50%" 는 아무 뜻이 없다.
`rate_reliable` 이 false 면 화면에서 숫자를 감춘다. **숫자만 내보내면 사용자가 그 숫자를
목표로 삼는다.**

달성률은 `covered` 만 센다. `in_experience_only` 는 넣지 않는다 —
**가지고 있다는 것과 전달했다는 것은 다르다.** 자소서에 안 쓰면 읽는 사람은 모른다.

## 7. 남의 테이블을 읽지 않는다

공고는 C4(`job_postings`), 자소서·경험은 B(`resumes`·`experiences`) 소유다.
제가 직접 SQL 을 쓰면 **접근 통제·조회 로직이 두 곳으로 갈라진다** — A8 의 C6 어댑터와
같은 문제다. 그래서 이 패키지는 C4·B 모델을 import 하지 않고 **DB 드라이버 없이 테스트된다**.

### 공고 — **C 가 창구를 하나 열었다** ✅ (C 답변 2026-10-22)

```python
# app/app/postings/read.py  (C 소유)
get_posting_fields(session, posting_id) -> dict | None
# 키 = PostingIn 필드와 동일. 원문 그대로(mask·C5 는 A11 이 한다)
```

A 는 이 함수만 부르고 `JobPosting` ORM 은 모른다 → **C4 가 컬럼을 바꿔도 그 함수 한 곳만
고치면 된다.** API 가 `posting_id` 를 받는 경로가 이걸 쓴다.

구현에서 정한 것 세 가지.

| 결정 | 이유 |
|---|---|
| `posting` 과 `posting_id` 중 **하나만** 받는다 (422) | 둘 다 받으면 어느 쪽이 이기는지 호출자가 알 수 없다 — 화면에서 고친 값을 보냈는데 저장된 원본으로 분석되면 **결과가 조용히 달라진다** |
| 분석할 본문·요건이 전부 빈 공고는 **422** | C 창구는 검토대상(`needs_review`) 공고도 돌려준다. 그런 공고는 필드가 비어 있을 수 있고, 500 으로 흘리면 사용자는 고장으로 본다 |
| 창구를 **짧은 세션**으로 부른다 (`Depends(get_db)` 아님) | 이 엔드포인트는 LLM 때문에 응답이 최대 30초다. 요청 단위 세션을 받으면 **모델을 기다리는 동안 커넥션 풀 자리를 잡고 있는다.** 공고 조회는 모델 호출 전에 끝나는 읽기 한 번이다 (**@D** 확인 부탁) |

**C 창구의 키와 `PostingIn` 필드가 같은지 테스트로 대조한다** — `PostingIn` 은
`extra="forbid"` 이라 C 가 키를 더하면 실행 중에 터진다. C 브랜치가 머지되기 전에는
`importorskip` 으로 건너뛴다 (A8 이 B11 상수를 대조하는 것과 같은 방식).

### ★ 미결 — 사용자 입력 공고의 권한 검사

`source='user'` 공고는 **"해당 사용자만 조회"** 가 규약인데(`models/posting.py` SOURCES),
C 창구는 `session.get(JobPosting, posting_id)` 라 **소유자로 걸러 주지 않는다.**

> **@C** — `get_posting_fields(session, posting_id, *, user_id)` 로 받아, 남의 비공개
> 공고면 `None` 을 돌려주시면 좋겠습니다. 제가 여기서 `owner_user_id` 를 직접 보면
> **조회 경로를 하나로 모은 합의가 깨집니다.**

## 9. 구현 중에 잡은 버그 — 한국어에 낱말 경계가 없다

**공백을 지워 대조하면 `tech_stack` 배열이 통째로 안 잡힌다.**

```
"Django Docker PostgreSQL"  →(공백 제거)→  "djangodockerpostgresql"
→ 세 낱말이 한 낱말이 되어 **하나도** 안 잡힌다
```

처음에는 `"Node.js"` 와 `"node js"` 를 같게 보려고 공백을 전부 지웠다. 그러면 낱말 경계가
사라진다. **경험의 `tech_stack` 을 이어 붙이면 바로 이 모양이 된다** — 사용자는 쓴 기술을
전부 "없다" 고 듣는다.

고친 방법: 공백은 남기고, **별칭을 "구분자가 있어도 없어도 맞는 패턴"으로** 바꿨다.

```
별칭 "Node.js"    →  node[\s._\-/]*js      ← "node js" · "nodejs" 둘 다
별칭 "자바 스크립트"  →  자바[\s._\-/]*스크립트
```

사전 작성 규칙이 하나 생겼다 — **별칭은 띄어 쓴 형태로 적는다.** 단 **없는 공백을
만들지는 않는다**: `"한글"` 을 `"한 글"` 로 적으면 **"작성한 글"** 이 걸린다.

같이 잡은 것들.

- `"자바 스크립트"` 가 Java 로도 집계됐다 → 긴 별칭부터 보고 **잡은 자리를 덮는다**
- `"컴퓨터활용능력 1급"` 이 안 잡혔다 → 뒤의 숫자는 **급수·버전**이라 거절하지 않는다
  (`Python3`·`Java8` 도 같은 이유). 뒤에 **글자**가 오면 다른 낱말이다(`java|script`)
- `"뷰"`(Vue)가 **"인터뷰"·"리뷰"** 안에서 걸렸다 → 한 글자 한글 별칭을 **사전 조립 때 거부**

> **교훈: 영문 기준으로 만든 대조 규칙은 한국어에서 다르게 틀린다.**
>
> 영문은 앞뒤 ASCII 검사로 낱말 경계를 잡을 수 있지만 **한글은 그 방법이 통하지 않는다.**
> C5 인젝션 패턴, A1 PERSON 규칙, B4 글자 수 세기도 같은 성질의 문제를 안고 있습니다.
