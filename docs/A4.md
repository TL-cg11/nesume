## 1. 무엇을 정하는 문서인가

A3(질의 분류)·C6(검색 필터)·A5(출력 검사)가 **각각** 판정을 내린다. A8이 그 셋을 합쳐
감사 로그(B3) **한 행**으로 남긴다. 세 단계가 같은 모양으로 말하지 않으면 합친 결과가
의미를 갖지 못한다. 그 모양을 한 곳에 정의한다.

```
A3 classifier ─┐
C6 retriever  ─┼─→ A8 merge ─→ audit_logs 1행 (B11)
A5 output_guard┘
```

## 2. 판정은 세 값이다 — `flag`는 판정이 아니다

`tasks.md` A4에는 처리가 `allow/block/mask/flag` **네 값**으로 적혀 있다.
그런데 **이미 머지된 코드가 세 값을 쓰고 있다.**

| 근거 | 내용 |
|---|---|
| `models/audit.py` | `DECISIONS = ("allow","block","mask")` — **DB CHECK 제약** |
| `policy/matrix.yaml` | 모든 칸이 `allow`/`block`/`mask` |
| `policy/policy.py` | `decision()`이 그 셋만 반환 |
| `tasks.md` A3 | "권한 외는 **flag만**, 하드 차단은 명시 패턴 한정" |

마지막 줄이 핵심이다. 권한 밖 질의는 **막지 않고 표시만** 남긴다 — 즉 판정은 `allow`이고
`flags`에 표식이 붙는다. `flag`를 네 번째 판정으로 두면 "flag인데 통과시킨다"는
모순된 상태가 생긴다.

**결론: 판정 3값 + `flags` 배열.** `tasks.md` A4의 문구를 수정하는 것을 제안한다.

## 3. 구조

```python
@dataclass(frozen=True)
class Finding:
    rule_id: str              # ≤ 50자 (audit_logs.rule_id 컬럼 길이)
    severity: Severity        # info | warn | critical
    count: int = 1

@dataclass(frozen=True)
class Verdict:
    decision: Decision                  # allow | block | mask
    stage: DecisionStage                # classifier | retriever | output_guard
    findings: tuple[Finding, ...] = ()
    query_type: QueryType | None = None # 분류 단계에서만
```

**`Finding`에 값을 담지 않는다.** 종류·심각도·개수만 담는다. 걸린 내용을 담으면
감사 로그와 화면에 그 값이 그대로 남는다 — A1의 `Hit`과 같은 판단이다.

**`severity`에서 판정을 자동으로 끌어내지 않는다.** 같은 `warn`이라도 입력 단계에서는
표시만 하고 출력 단계에서는 가리는 식으로 다르다. 판정은 각 단계가 정하고, `Finding`은
사실만 나른다.

### 파생값 — 감사 로그 컬럼에 대응

| 속성 | 대응 컬럼 | 규칙 |
|---|---|---|
| `.flags` | `flags` ARRAY | 걸린 순서 유지, 중복 제거 |
| `.rule_id` | `rule_id` (단일!) | **가장 무거운 것, 동률이면 먼저 걸린 것** |
| `.canary_hit` | `canary_hit` BOOL | `LEAK_CANARY`가 있으면 True |

`rule_id` 컬럼이 **하나뿐**이라 여럿 걸렸을 때 무엇을 남길지 정해야 한다. 나머지는
`flags`에 남으므로 잃는 정보는 없고, 대시보드(D15)에서 "무엇 때문에 막혔나"를 바로 볼 수 있다.

## 4. 합치기

```python
v = classifier_verdict.merge(retriever_verdict).merge(output_verdict)
await write_audit_log(request_id=..., user_id=..., latency_ms=..., **v.to_audit_fields())
```

| 항목 | 규칙 |
|---|---|
| 판정 | 더 무거운 쪽 (`block` > `mask` > `allow`) |
| 단계 | **무거운 판정을 만든 단계.** 동률이면 앞쪽 단계 |
| 표식 | 순서대로 합치고 중복 제거. 같은 규칙은 개수 합산·무거운 심각도 |
| 질의 유형 | 먼저 정해진 값 유지 (분류 단계가 한 번만 정한다) |

단계를 "무거운 판정을 만든 쪽"으로 남기는 이유는 **어디서 막혔는지가 로그의 쓸모**이기
때문이다. 동률일 때 앞쪽을 남기는 이유는 파이프라인 앞쪽이 원인이기 때문이다.

## 5. 길이를 검사하는 이유

`Finding` 생성 시 `rule_id` 길이를 검사하고 넘으면 `ValueError`를 던진다.

감사 로그는 **B11이 요청 종료 시 `finally`에서 한 번** 쓴다. 거기서 INSERT가 실패하면
**그 요청의 감사 기록만 통째로 사라진다** — 하필 뭔가 걸렸던 요청이다. 값을 만드는
쪽에서 미리 막는다.

## 6. DB 제약과 자동 대조

`tests/guardrail/test_schema.py`가 `models/audit.py`의 상수·컬럼 길이와 **직접 대조**한다.

```python
from app.models.audit import DECISIONS as DB_DECISIONS
assert set(DECISIONS) == set(DB_DECISIONS)
assert AuditLog.__table__.c.rule_id.type.length == MAX_RULE_ID_LEN
assert set(v.to_audit_fields()) <= set(AuditLog.__table__.c.keys())
```

두 곳에 적힌 값 목록은 **반드시 갈라진다**. 갈라지는 순간 테스트가 깨지게 해 두는 것이
문서에 "맞춰 주세요"라고 적는 것보다 낫다. 실제로 `QUERY_TYPES`에서 값 하나를 빼 보니
테스트 2건이 깨지는 것을 확인했다.

> 이 테스트 파일은 A 파트 테스트 중 **유일하게 B의 모델을 import**한다. 대조가 목적이라
> 어쩔 수 없다. DB에 접속하지는 않고 테이블 메타데이터만 읽지만, `app.db`를 거치므로
> `DB_*` 환경변수가 필요하다(테스트 하네스에는 있다).

## 7. 각 파트에 요청

**B** — `write_audit_log`(B11)에서 `**verdict.to_audit_fields()`로 펼쳐 쓰시면 됩니다.
키 이름이 컬럼과 같은지 테스트로 고정했습니다. 나머지 컬럼(`request_id`·`user_id`·
`latency_ms` 등)은 A8이 채웁니다.

**C** — C6 검색 필터 결과도 `Verdict(stage="retriever")`로 만들어 주시면 A8이 합칩니다.
`policy.decision()`이 돌려주는 값이 그대로 `Verdict.decision`에 들어갑니다.

**D** — `audit_logs`의 값 목록(`DECISIONS`·`QUERY_TYPES`·`DECISION_STAGES`)이 바뀌면
이 모듈도 함께 바뀌어야 합니다. 테스트가 잡아주지만 변경 시 알려주시면 좋겠습니다.
